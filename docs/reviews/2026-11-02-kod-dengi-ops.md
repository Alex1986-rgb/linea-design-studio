## Высокий

**В1. Расторжение обнуляет вознаграждение: обход площадки.** `lib/contract.php:253-270, 389-402`.
Сценарий: договор подписан, контакты открыты, любая сторона предлагает расторжение с `acc = 0`, вторая подписывает кодом. Вознаграждение пересчитывается от принятого (`brig_commission(0)` = 0), `commission_due_at` не ставится, дальше стороны работают напрямую. Пола нет: ни аванс по реестру (`brig_paid_kop`), ни выставленный счёт не удерживают базу. Если счёт уже выставлен, `commission_kop` всё равно понижается сразу, админу уходит только письмо.
Опция `termination_fee_base = 'paid'` разрешена в `boot.php:192`, но код (`contract.php:395`) обрабатывает только `'accepted'`. При `'paid'` вознаграждение не пересчитывается вовсе, то есть остаётся от полной цены. Поведение противоположно названию.
Исправление: база = max(принятое + extra, оплачено по реестру, уже выставленный счёт). Либо расторжение до первого принятого этапа требует подтверждения LINEA. Реализовать `'paid'`.

**В2. Включение `yk_receipt` отправит «второй чек» по всем старым заказам.** `tools/cron.php` (шаг 8), `lib/yookassa.php:139-170, 197`.
Cron берёт все `delivered` с `paid_by LIKE 'yookassa %'` и `receipt2_id IS NULL`. Признака «первый платёж был с чеком» в базе нет. Для платежей, созданных без `receipt` (самозанятый, чек в «Мой налог»), второй чек с `settlement prepayment` будет отклонён или задвоит доход. Чек возврата со старого платежа получит признак `full_prepayment`, которого в кассе не было.
Исправление: колонка или дата `yk_receipt_since`; второй чек и API-возврат только для заказов, созданных после включения флага.

**В3. Бэкап принимает «пустую» базу, а ротация стирает хорошие копии.** `tools/ops/bk.mjs:checkTgz, rotate, upload`.
- `checkTgz` проверяет таблицы только при `driver === 'mysql'`. Дамп с `driver: 'none'` (нет ни MySQL, ни SQLite) проходит. Нет сверки с прошлым удачным бэкапом: строк в `orders` стало 0 или размер упал на 90 % — всё равно «ok». За 14 суток такие копии вытесняют все хорошие (`keepDaily`).
- Чистка на Диске идёт по возрасту (`--min-age`), а не по числу копий. Если бэкап перестал проходить, через 15 суток (daily) и 59 суток (weekly) на Диске не останется ничего. Локальные копии лежат только на SmartApe.
Исправление: отказ при `driver === 'none'`; отказ при падении числа строк или размера более чем на 30-50 % к `backup-last-ok.json`; на Диске удалять только при наличии не менее N более свежих копий.

**В4. Ключ SmartApe на Beget даёт оболочку на весь аккаунт.** `tools/ops/after-beget-up.sh` (строка `LINE=`).
Ограничено только `from=`, `command=` нет. Компрометация SmartApe даёт чтение и запись во все сайты аккаунта Beget, включая чужие. Лучше `command="bash ~/linea-ops/beget-dump.sh"` (скрипт положить заранее) плюс `restrict`.

## Средний

**С1. Расторжение: акт устаревает.** `remont.php:218-236` (`stage_accept`) не проверяет открытый черновик расторжения. Предложили при acc = X, заказчик принял ещё этап, подписали. В акте и в базе вознаграждения старое X, а принято больше. Блокировать приёмку при черновике или пересчитывать акт перед подписью. Обратный случай: после допсоглашения, снижающего цену, стоимости этапов не пересчитываются (`brig_job_stage_amounts`), `acc` > `total`, и `contract.php:263` не даёт расторгнуть с невнятным текстом.

**С2. Возвраты: зависшие операции и двойной возврат.** `lib/yookassa.php:yk_refund`.
- Запись `sent` создаётся до вызова API. Падение процесса или таймаут после создания возврата у ЮKassa: запись остаётся `sent` или `failed` без `provider_id`. Вебхук `refund.succeeded` отбрасывается (`yk_known_refund`), `refunded_kop` не растёт. `sent` учитывается в `yk_refund_left` вечно.
- Повтор с другой суммой берёт новый ключ идемпотентности, возможен второй возврат (потолок — сумма платежа на стороне ЮKassa). Ключ ЮKassa живёт 24 часа.
- Вебхук, пришедший раньше записи `provider_id`, теряется (мы отвечаем 200, ЮKassa не повторяет).
- Сверки висящих возвратов в cron нет.
Исправление: cron-сверка `pending/sent` через `GET /refunds`; при `failed` без ответа сначала искать возврат по платежу (`GET /refunds?payment_id`).

**С3. Два пути «возврат».** `panel.php:138-148` (смена статуса на `refunded`) ничего не списывает и не трогает `refunded_kop`, после этого API-возврат закрыт (`yk_refund` требует paid/delivered). Ручной путь `panel.php:188-191` читает `refunded_kop` без блокировки: двойной клик пишет две строки `pay_ops` и одно приращение. Убрать `refunded` из ручной смены статуса или связать с `o_refund`.

**С4. Признак расчёта в чеке возврата выбирается в момент создания** (`yookassa.php:197`). Если возврат ещё не проведён, а выдача альбома отправила второй чек (`full_payment`), чек возврата уйдёт с `full_prepayment`. Окно узкое.

**С5. Автоудаление ПДн: пропущены условия.** `lib/kabinet.php:593-606`.
Шаг 1 (сделки старше `retention_years`) не проверяет открытые споры (`br_disputes`), неоплаченные счета и вознаграждение (`br_invoices`), неподтверждённые платежи реестра. Текст договора заменяется заглушкой необратимо. Нижняя граница `retention_years` = 1 (`boot.php`, граница `[1,10]`) при сроке исковой давности 3 года: админка может поставить 1. Поднять минимум до 3-5.
Перед первым боевым запуском: `cron.php --pd-dry` и свежий бэкап. Журнал есть (`pd.log`, аудит), но восстановление только из бэкапа. Заказ с `receipt2_id IS NULL` обезличивается, и чек потом не уйдёт (нет e-mail), а cron повторяет попытку каждые 15 минут без ограничения и без паузы.

**С6. Второй шаг входа: блокировка владельца и зависимость от IP.** `admin.php:adm_2fa_need/adm_2fa_send`.
- В режиме `auto` включается, как только заданы `admin_emails` и `brig_mail_enabled`. Результат `brig_mail` не проверяется. Письмо ушло в спам или не доставлено: владелец заперт, лечение только правкой config по SSH или аварийным IP. Сейчас смягчено 9d25cf14 (`admin_2fa=false` в выкладке), включать только после проверки доставки на домене.
- Обход 2FA аварийными IP и `admin_ip_allow` держится на `linea_ip()`, то есть на том, что nginx Beget перезаписывает `X-Real-IP`. Скрипт выкладки (шаг 6) проверяет только честный запрос. Добавить проверку с поддельным `X-Real-IP: 1.2.3.4`: `linea_ip` не должен совпасть.

- Обход через `admin-brigady.php`/`panel.php` не найден: оба требуют `$_SESSION['adm']`, а он ставится только в `adm_enter()`.

**С7. Мониторинг.** `tools/ops/monitor.mjs`.
- Проверка `ping` читает только публичный ответ. `cron.last` и версия схемы доступны по токену, но монитор токен не использует: умерший cron (чеки, автоудаление, напоминания) незаметен. Добавить `monitor_token` в `ops.json` и проверку возраста `cron_last` (> 45 мин).
- `expectBackup` по умолчанию `false` (включает `after-beget-up.sh`). Пока скрипт не запущен, отсутствие бэкапа не сигналит.
- `ping.php`: лимит `ping-token` проверяется до сверки токена, то есть 30 неверных попыток блокируют и настоящий монитор, если `linea_ip` у всех одинаковый (прокси не в `trusted_proxies`). Токен допускается и в `?token=` — попадёт в журналы доступа; оставить только заголовок.

**С8. `tools/vykladka-kabinety.sh`.**
- Повторный запуск перезаписывает `brig_mail_enabled`, `admin_emails`, `notify_enabled` без `isset`: правки владельца (дополнительные адреса, отключённые письма) теряются.
- `STAMP` с точностью до минуты: второй запуск в ту же минуту затирает `config.php.bak-<STAMP>` уже изменённой копией, оригинал потерян. Копии с секретами копятся, не чистятся.
- `file_put_contents` не атомарен: в момент записи сайт читает обрезанный config. Писать во временный файл и `rename`.
- `var_export` теряет комментарии и выражения (`getenv`, константы). Откат только вручную (`cp config.php.bak-…`), скрипта отката нет.
- Токен монитора передаётся в `curl -H` (виден в `ps` на маке в момент вызова). Некритично.

## Низкий

- 7z получает пароль в командной строке (`-p…`), на SmartApe виден администраторам. Пароль архива хранится только на SmartApe; копирование в менеджер паролей — ручной шаг из документации, ничем не проверяется.
- `beget-dump.sh`: резервный PHP-дамп без единого снимка (нет транзакции); большие файлы (> `LINEA_BK_MAXMB`) пропускаются и пишутся в `skipped-big.txt`, но проверка бэкапа об этом не сообщает; при SIGKILL во временной папке Beget остаётся полный дамп с ПДн.
- `restore-check.sh --keep` оставляет ПДн в `$TMPDIR`; проверка восстановления ставится только один раз (нет регулярной).
- Публичный `ping.php` показывает `private`/`config`/`sqlite`/`zip` без токена (мелочь).
- Повтор второго чека с ключом `rcpt2-<номер>` спустя 24 часа после потери ответа создаст дубль. Крайний случай.

## Проверено и в порядке

- Подделка вебхука `refund.*`: id ищется в своей базе (`pay_ops`), статус и сумма берутся из API (`yk_refund_settle`), суммы сверяются.
- Применение возврата атомарно (`UPDATE … WHERE status <> 'succeeded'`): вебхук и ответ API не задвоят `refunded_kop`.
- Возврат больше оплаченного закрыт `yk_refund_left` (с учётом возвратов в пути). Признак расчёта второго чека: `full_payment` + `settlement prepayment`, схема верна. Ставка НДС `1` = «без НДС».
- Подпись документов: сторона берётся из точки входа (`remont.php` — client, `brigada/jobs.php` — brigade), документ привязан к сделке (`job_id`); код одноразовый, 5 попыток засчитываются до сверки, `hash_equals`. Расторжение после завершения невозможно (`status !== 'work'`).
- `ping.php`: `hash_equals`, токен не короче 24 знаков, неверный токен — 403 + пауза. Подробности без токена не отдаются.
- Пароль MySQL передаётся `mysqldump` через `MYSQL_PWD`, в логах не появляется; в архиве `sessions/`, `rate/`, `exports/` исключены; шифрование 7z AES-256 с `-mhe=on`.
