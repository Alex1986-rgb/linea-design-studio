## Высокий

### В-1. Все старые ссылки `order.html?t=` ведут на «Ссылка устарела» (гостевой режим не работает в браузере)
- `site/js/kabinet.js:315-320`: ветка `#t=` вызывает `vh('link')` ДО `vh('me')`, `ME.csrf` пуст, `X-CSRF: ''` → `acc_csrf_check` (`lib/accounts.php:36`) отвечает 403 → `loginView('Ссылка устарела')`. Проверено в браузере на dev-сервере. Тесты ходят в API напрямую с csrf и этого не ловят.
- Правка: в ветке `tk` сначала `ME = await vh('me')`, потом `link`. Добавить браузерный/смоук-тест перехода `order.html?t=`.

### В-2. Cron шлёт письма и сигналы каждые 15 минут по заказам без `account_id`
- `server/tools/cron.php:40-52` + `lib/kabinet.php:243-247`: `kab_notice()` при `account_id <= 0` молча выходит, запись с `ukey` не создаётся, проверка `COUNT(notices WHERE ukey)` всегда 0 → напоминание клиенту (письмо), `brig_signal`, `brig_admin_notify` повторяются каждый запуск. Миграция v4 добавляет `orders.account_id` пустым, бэкфилла нет (`migrations.php:257`): все заказы до v4 не привязаны, пока клиент не войдёт кодом.
- Сценарий: сделка в работе, этап «готов к приёмке», заказ старый → клиенту письмо каждые 15 мин, админу сигнал и письмо каждые 15 мин.
- Правка: бэкфилл в v4 (`UPDATE orders SET account_id = (SELECT id FROM accounts WHERE role='client' AND email=LOWER(orders.email))`, а для почт без аккаунта — создание); дедупликацию в cron вести не по `notices`, а по отдельной таблице/полю (`stage.remind_sent`); `kab_notice` без аккаунта не должен считаться «отправлено». Тест: cron дважды подряд на заказе без аккаунта.

## Средний

### С-1. Блокировка входа чужой почты (DoS)
- `lib/kabinet.php:118-120`: лимит «5 кодов в час на адрес» считается по запросам и молча отказывает; 5 запросов `code` на почту жертвы (с разных IP или за 20/час с одного) лишают её письма с кодом на час, при этом ответ «всё хорошо». Каждый новый код ещё и аннулирует предыдущий (`:123`) — жертва с уже полученным кодом получает «устарел».
- Правка: не аннулировать действующий код при повторном запросе в первые 60 с и отдавать тот же; лимит на адрес поднять (10/ч), счёт — отдельно от IP; для адреса, у которого есть роль, не прятать отказ («код уже отправлен, подождите N минут»).

### С-2. Почта брифа не подтверждена, но заказ и аккаунт создаются сразу
- `brief.php:128-136`, `kab_client_account()` (`lib/kabinet.php:91-103`): любой может создать бриф на чужую почту → аккаунт клиента для этой почты и чужой заказ в кабинете жертвы; письма LINEA («Бриф получен», сообщения админа) идут жертве; токен остаётся у отправителя и после привязки (гостевой доступ к заказу, куда жертва потом пишет ответы и сообщения, `kb_lenta`). Захвата аккаунта нет (вход только кодом на почту), но есть спам, подмена контекста и утечка ленты по токену. Аккаунты создаются без лимита по почте (рост таблицы при 5 брифах/ч с IP).
- Правка: привязывать заказ к аккаунту только после подтверждения почты кодом (как в `vhod.php:65`); `brief.php` аккаунт не создаёт; при привязке/перепривязке (`panel.php` `o_rebind`) выпускать новый токен заказа.

### С-3. Бригадный аккаунт, заведённый на чужую почту, получает вход кодом
- `kab_roles_for()` (`:84`) даёт роль `brigade` любому активному недемо-аккаунту; регистрация бригады с чужой почтой + своим паролем возможна (почта не подтверждается). Настоящий владелец почты входит кодом в аккаунт злоумышленника, а пароль злоумышленника продолжает работать.
- Правка: при первом входе кодом в бригадный аккаунт без `email_verified_at` — сброс пароля (требовать установку нового) и отзыв прежних сессий; подтверждать почту при регистрации.

### С-4. Серия допсоглашений обходит порог «−20 %»
- `lib/contract.php` (`$needsAdmin = $delta < 0 && -$delta*100 > $base*pct`): порог считается от текущей цены `$base`, а не от исходной; пять допсоглашений по −19 % уменьшают базу вознаграждения почти втрое, оба подписывают их кодами. Закрытие В-1 прошлого ревью неполное.
- Правка: порог — суммарное уменьшение относительно `deal_total_kop` первоначального договора; комиссия не ниже `max` выставленного/первоначального при отмеченной выплате.

### С-5. Миграции без блокировки и без устойчивости к повтору
- `lib/db.php:121-128`: два одновременных первых запроса (cron + сайт при выкладке) оба выполняют v3/v4; на MySQL DDL не откатывается, второй падает на `Duplicate column`, а все следующие запросы бегут по тем же шагам с начала и падают вечно (особенно `DROP INDEX request_id`, `CREATE INDEX br_jobs_request` v3).
- Правка: `GET_LOCK('linea_migrate')` / файловая блокировка; каждый шаг в `try` с игнором кодов «уже существует»; версия обновляется после шага, а не после пачки.

### С-6. Сессии «запомнить на 30 дней» не переживут сборку мусора PHP
- `lib/accounts.php:14-27`, `kab_login`: кука продлевается до 30 дней, но `session.gc_maxlifetime` остаётся 1440 с; файлы в `linea-private/sessions` удаляются сборщиком (где он включён), а где выключен (Debian/Beget) каталог растёт без чистки. Заодно сессия не привязана ни к чему (UA/IP) — украденная кука живёт 30 дней.
- Правка: `ini_set('session.gc_maxlifetime', 30*86400)` в `acc_session`, чистка каталога в cron, привязка к устройству (`acc_devices`) с проверкой при каждом запросе (сейчас `kab_client` проверяет только `ended_at`, и то если запись есть).

### С-7. Значимые действия ремонта доступны гостю без кода: `invite`, `msg`, `dispute_msg`
- `remont.php` список `kab_require_fresh_for_order` не включает `invite`, `msg`, `dispute_msg`: держатель одной ссылки пишет бригаде от имени клиента (после открытия контактов — без фильтра) и приглашает бригады. Если решение осознанное — зафиксировать; иначе добавить в список.

## Низкий

- `cron.php:82`: `kab_notice(1, null, 'proekt', 'holidays', …)` — маркер записывается уведомлением в аккаунт №1 (случайный клиент или бригада увидит «holidays»). Вынести маркер в `settings`.
- `kab_is_workday` не знает рабочих суббот-переносов (только выходные + таблица `holidays`); сроки 2026–2027 будут на день-два короче в такие недели. Таблица праздников кэшируется `static`, правки админа вступают в силу со следующим запуском — норма.
- Тайминг `code`: неизвестная почта — `usleep(200 мс)`, известная — запись + `mail()`; разницу в ответе видно, перечисление почт возможно по времени ответа. Выровнять, отправляя письмо после ответа (`fastcgi_finish_request`).
- `site/js/kabinet.js`: `esc()` не экранирует `'`; `last.url` (ссылка выпуска, вводит админ) идёт в `href` без проверки схемы — `javascript:` только от администратора. Разрешить только `https:`.
- Ответы К-N: `answers.json` читается и пишется без общей блокировки (`kab_answers` / `kab_answers_save`) — два одновременных ответа теряют один; повторный `decide` перезаписывает прежнее согласие (подписи в `signatures` остаются, но `answers.json` показывает последнее).
- `linea_https()` доверяет `X-Forwarded-Proto` от клиента, `linea_local()` — заголовку `Host`; безопасно только пока nginx всегда перезаписывает `X-Real-IP` на каждом location (иначе `Host: localhost` включает `test`-режим и обход https-запрета). Проверить конфиг nginx на Beget.
- Письма `kab_notice` подставляют названия этапов (вводит бригада) в тело — контакты фильтруются `brig_guard`, но текст от бригады приходит в фирменном письме LINEA; ссылки в нём не вырезаются.
- `consent_revoke` для `project_to_brigades` отменяет подбор, но уже разосланные пакеты у бригад остаются доступны по `br_files` (проверить `brig_file_allowed` на статус запроса `cancelled`).

## Проверено, дефектов не найдено
- Перебор кода входа: счётчик атомарный (`UPDATE … tries < 5`), код одноразовый (`used_at IS NULL`), HMAC, 25 попыток/час на адрес против 900 000 вариантов.
- Фиксация сессии: `session_regenerate_id(true)` в `kab_login`, `acc_start`, `link` (для гостя); `use_strict_mode`; куки HttpOnly, SameSite=Strict, Secure по https.
- CSRF: POST в vhod/kabinet/panel требуют токен сессии; remont.php — HMAC токена плюс SameSite=Strict.
- IDOR: `kab_order_access` (аккаунт или один гостевой заказ), `pd`-файл по `account_id`, уведомления/устройства/согласия по `account_id`; `kab_require_fresh_for_order` сверяет аккаунт или почту заказа — чужой заказ с «свежим» кодом не подписать.
- Эскалация: роль `admin` из `admin_emails` ничего не даёт без пароля `admin.php` (панель проверяет `$_SESSION['adm']`); выбор роли ограничен ролями почты.
- Журнал админа: все изменяющие действия панели пишут `brig_audit` с IP; обхода через GET не нашёл.
- Контакты бригады/клиента: кабинет клиента не отдаёт контактов до `contacts_open_at`; протокол `doc` экранирован и под CSP `default-src 'none'`.
- ПДн: выгрузка и удаление привязаны к `account_id` заявки; ZIP отдаётся только владельцу и после свежего кода.
