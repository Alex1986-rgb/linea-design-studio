## 0. Что уже решено и что делает параллельная ветка

**Правила владельца (01.11.2026) — не обсуждаются в этом документе, только реализуются:**
1. Платных откликов, лидов, допуска нет.
2. Удержание на платформе = **гарантия сайта** (приёмка этапов по чек-листам, арбитраж) + **листы по запросу** под бригаду

3. Комиссия с бригады **10 %**; пилот — первые 5 бригад, их первые 3 сделки — **5 %**. Становится к оплате **при первых деньгах бригаде**

4. Все договоры — только через сайт: собираются из сделки, подпись ПЭП кодом на почту обеих сторон (время, IP, sha256 версии),

   Журнал сделки виден обеим сторонам.
5. До подписания — общение только в ленте сделки с фильтром контактов.
6. Оплата ремонта пока вне сайта (стороны отмечают аванс/этапы). Безопасная сделка ЮKassa — позже, после ИП; включение без переделки.
7. Демо-бригады — только «образец», вне подбора.

## 1. Роли

### 1.1 Клиент (заказчик проекта и ремонта)
- Физлицо-потребитель. С брифа — клиент дизайн-проекта; когда проект **оплачен** — ещё и заказчик ремонта. Без оплаченного проекта подбора нет.
- **Вход.** Сейчас — только ссылка `order.html?t=…` (токен заказа). Будет: аккаунт `accounts.role = 'client'` по почте из брифа,
  вход **кодом на почту**, без пароля (подробно — 3.0 и 4А.1). Ссылка с токеном продолжает работать и ведёт в кабинет (гостевая сессия заказа),
  но **значимые действия** требуют свежего входа по коду (не старше 12 часов) — закрывает В-5 из ревью техники.
- Один клиент — может иметь несколько заказов (квартира + дача) → в кабинете список объектов.
- **Доверенное лицо** (муж/жена, прораб заказчика) — роль «наблюдатель по приглашению»: видит сделку и ленту, пишет в ленту, **не подписывает
  и не принимает**. Приглашение по почте, отзывается клиентом. Этап 2 (не MVP).

### 1.2 Бригада
Юридическая сторона договора — **бригада** (`br_brigades`, один ИНН = одна бригада). Внутри — люди с ролями:

| Роль в бригаде | Кто | Может | Не может |
|---|---|---|---|
| **Владелец** | ИП/руководитель ООО/самозанятый мастер, на кого ИНН | всё: анкета, предложения, подпись договора и допсоглашений ПЭП, деньги и счета, пригласить/удалить людей | — |
| **Бригадир** | ведущий объект | лента сделки, фото этапов, «готов к приёмке», закрытие замечаний, листы по запросу, предложение (черновик) | подписывать, отправлять предложение, видеть «Деньги», менять анкету |
| **Сотрудник** | мастер на объекте | фото этапов своего объекта, листы по запросу, читать ленту | писать клиенту в ленту (по настройке владельца), всё остальное |

- Технически: таблица `br_members (brigade_id, account_id, role owner|foreman|worker, objects JSON|null, invited_at, removed_at)`;
  владелец — запись с `role=owner`, создаётся при регистрации (сегодняшний `br_brigades.account_id`). Бригадир/сотрудник может быть
  привязан к конкретным объектам (`objects`) — видит только их.
- Подписывает **всегда владелец** (ПЭП — от имени стороны договора). Если у ООО подписант не владелец аккаунта — поле «подписант,
  должность, основание (доверенность №)» в анкете, код уходит на его почту.
- В карточке клиенту показывается бригада и **бригадир объекта** (имя — после подписания договора; до — «бригадир будет указан в договоре»).

### 1.3 Администратор (Александр)
Все права. Единственный, кто: допускает/блокирует бригаду, решает споры, списывает/корректирует комиссию, меняет `brig_terms`,
замораживает сделку, видит контакты обеих сторон до подписания (только для спора/жалобы, с записью в журнал «просмотр контактов»).
Вход — как сейчас `admin.php` (пароль) + **второй фактор кодом на почту/Telegram** для денежных и блокирующих действий (п. 5.12).

### 1.4 Модератор (на будущее)
Роль `accounts.role = 'moderator'` под тем же входом в админку, права по списку:

| Действие | Модератор | Админ |
|---|---|---|
| Проверка анкеты, ИНН, видеозвонок, отметки | да | да |
| Допуск бригады | предлагает («рекомендую допустить») | решает |
| Приостановка (временно, до 7 дней) | да, с причиной | да |
| Блокировка, снятие блокировки | нет | да |
| Сигналы обхода: разметка «ложный / подтверждён» | да | да |
| Споры: переписка, сбор доказательств, проект решения | да | да |
| Решение спора, деньги, комиссия, счета, списание | нет | да |
| Скрытие отзыва по правилам | да | да |
| Настройки `brig_terms`, экспорт ПДн | нет | да |

Все действия модератора и админа — в журнал (п. 5.11). В MVP модератора нет, но **проверка прав сразу через функцию `adm_can($action)`**,
а не через «вошёл в admin.php» — тогда роль добавляется без переделки.

### 1.5 Система
Таймеры (cron раз в 15 минут: `server/tools/brig-cron.php`), воркер листов (токен), фильтр контактов, расчёт комиссии. Действия системы
пишутся в журнал сделки как «Система: …».

## 2. Машина состояний сделки

### 2.1 Объекты и их связь
```
orders (проект оплачен)
  └─ br_requests  «Подбор бригады»     — один активный на заказ (повторный — после закрытия прошлого)
       ├─ br_invites / br_offers        — приглашения и предложения бригад
       └─ br_jobs   «Сделка»            — одна активная на запрос; при смене бригады старая закрывается, новая создаётся
            ├─ br_contracts / br_addenda — договор (версии) и допсоглашения, ПЭП обеих сторон   [ветка параллельного разработчика]
            ├─ br_payments    НОВОЕ      — аванс, оплата этапов, доплаты: кто отметил, сумма, способ (offsite | safe_deal)
            ├─ br_stages / br_remarks    — этапы и замечания
            ├─ br_messages               — лента сделки (переписка + системные записи)   [ветка]
            ├─ br_sheet_reqs             — листы по запросу
            ├─ br_disputes               — споры
            └─ br_ledger      НОВОЕ      — проводки комиссии (начисление, корректировка, оплата, списание) → br_invoices
```

### 2.2 Статусы запроса (`br_requests.status`)

| Код | Для людей | Кто действует | Клиент видит | Бригада видит | Таймер / выход |
|---|---|---|---|---|---|
| `new` | Готовим запрос | админ: пакет, рассылка | «Готовим проект для бригад — обычно до 1 рабочего дня» | ничего | админ «Разослать» → `open`. 1 рабочий день без действия → напоминание админу |
| `open` | Бригады считают | бригады | «Разослано N бригадам, предложения до {дата}» + пришедшие предложения | запрос в ленте, срок | срок `deadline_at` (по умолчанию 3 рабочих дня). Пришло ≥1 и срок вышел → `choosing`; 0 → `empty` |
| `choosing` | Выберите бригаду | клиент | сравнение | «Ждём решения клиента» | 14 дней без выбора: напоминания на 3/7/12 день; на 14 → `expired` |
| `empty` | Предложений нет | админ | «Пока никто не откликнулся. Мы расширим поиск и напишем вам» | — | админ: досылка (`open`, новый срок) или закрыть |
| `chosen` | Бригада выбрана | → есть `br_jobs` | см. сделку | см. сделку | пока сделка жива |
| `expired` | Выбор не сделан | клиент | «Срок ответа бригад истёк. Обновить запрос?» → кнопка «Запросить заново» | запрос исчезает из ленты | «Запросить заново» → `open` с новым сроком; предложения прошлого круга помечаются «устарело», бригады могут обновить |
| `cancelled` | Подбор отменён | клиент/админ | причина | «Клиент отменил запрос» | финал |
| `closed` | Ремонт завершён | — | архив | архив | финал |

Предложение (`br_offers.status`): `draft` (только у бригады) → `submitted` → `updated` → `withdrawn` (бригада отозвала до выбора) /
`chosen` / `not_chosen` / `stale` (новый круг запроса) / `declined` (бригада отказалась от запроса без предложения — `br_invites.declined_at`).

### 2.3 Статусы сделки (`br_jobs.status`) — основная линия

| Код | Для людей | Кто действует | Клиент видит | Бригада видит | Уведомления | Таймеры |
|---|---|---|---|---|---|---|
| `contract` | Готовим договор | обе стороны: уточнения в ленте; система собирает договор | ленту, черновик договора (без контактов), «Подписать» неактивно до готовности | ленту, черновик, поле «Реквизиты для договора» | бригаде «Вас выбрали»; остальным — «выбрана другая» | 3 дня без действий → напоминание обеим |
| `signing` | Подписание | та сторона, что не подписала | «Вы подписали / ждём бригаду» или наоборот | то же | второй стороне «Подпишите договор» с кодом по кнопке | **7 дней** с момента отправки на подпись: напоминания 2/5 день; на 7-й → `contract` (версия «просрочена»), сигнал `sign_timeout` |
| `signed` | Договор подписан | бригада: начать, клиент: отметить аванс | контакты бригады и бригадира, договор PDF, этапы, «Отметить аванс» | контакты и адрес клиента, этапы, листы по запросу, «Аванс получен» | обеим «Договор подписан, контакты открыты»; админу | 14 дней без денег (аванс/этап 1) → сигнал `no_money_14d` и звонок админа |
| `work` | Ремонт идёт | бригада: этапы; клиент: приёмка, оплаты | этапы, оплаты, ленту, листы | этапы, листы, «Деньги по объекту» | по событиям этапов | см. 2.5 |
| `final_check` | Итоговая приёмка | клиент | «Все этапы приняты. Подтвердите окончание работ» + итоговый акт | «Ждём итоговый акт» | клиенту | 5 рабочих дней → напоминание; 10 → «односторонний акт» (2.6) |
| `warranty` | Гарантия | любая сторона: гарантийное обращение | акт, «Сообщить о дефекте», «Оставить отзыв» | гарантийные обращения | клиенту: просьба об отзыве (через 3 дня, 14 дней) | срок гарантии из договора (мес.) → `closed` |
| `closed` | Закрыт | — | архив, документы | архив | — | хранение 5 лет (п. 6, №27) |

`done` из текущего кода = `warranty` (переименовать при миграции: `done` → `warranty`, `done_at` остаётся датой итогового акта).

### 2.4 Ветки и «накладки» (флаги поверх статуса)

Статусы-ветки — это **финальные** выходы. Флаги (`br_jobs.flags` или отдельные колонки) — **накладываются** на основной статус и не
меняют его, чтобы после снятия вернуть сделку туда же.

| Ветка / флаг | Откуда | Кто | Что происходит | Клиент видит | Бригада видит | Деньги / комиссия |
|---|---|---|---|---|---|---|
| **Отказ бригады до подписи** → `declined_brigade` | `contract`, `signing` | бригада (с причиной из списка) | запрос возвращается в `choosing`, остальные предложения снова доступны (если не старше 14 дн), иначе «Запросить заново» | «Бригада отказалась: {причина}. Выберите другую» | — | комиссии нет; сигнал `decline_after_choose`; 2 таких за 90 дней → приостановка ленты на 14 дней |
| **Отказ клиента до подписи** → `cancelled_client` | `contract`, `signing` | клиент | как выше, клиент может выбрать другую или закрыть подбор | — | «Клиент отказался» | комиссии нет |
| **Расторжение после подписи** → `terminated` | `signed`, `work` | любая сторона через «Расторгнуть договор» = допсоглашение о расторжении (обе подписи) **или** односторонний отказ (уведомление через сайт) | фиксируется сальдо: принятые этапы, отмеченные оплаты | то же | то же | комиссия пересчитывается: база = сумма **фактически отмеченных оплат бригаде** (не меньше уже начисленной по первым деньгам? — нет: пересчёт вниз разрешён, переплата → кредит бригаде, п. 2.7) |
| **Смена бригады** | `work`, `terminated` | клиент (после расторжения) | новая сделка на тот же запрос с пометкой «продолжение»; пакет — остаток сметы (не принятые позиции); листы и история старой сделки клиенту остаются | «Подобрать бригаду на оставшиеся работы» | старая бригада — только свой архив | у новой — комиссия от новой суммы; у старой — по факту |
| **Спор** (флаг `dispute`) | `signing`…`warranty` | любая сторона «Открыть спор» | **заморозка спорного**: нельзя принимать/возвращать спорный этап, подписывать допсоглашения на спорную сумму; остальная сделка живёт | «Спор №…: ответ бригады до {дата}», ход спора | то же | счёт на комиссию по сделке не выставляется, пока спор о деньгах (срок оплаты ставится на паузу) |
| **Просрочка** (флаг `overdue`) | `work` | система | этап не «готов» через 3 рабочих дня после плановой даты и без допсоглашения о переносе | «Этап «…» просрочен на N дней. Написать бригаде / Предложить новый срок» | «Просрочка: предложите перенос допсоглашением» | — ; 2 просрочки > 14 дней → сигнал админу |
| **Заморозка** (флаг `frozen`) | любой | только админ (с причиной) | все действия сторон, кроме ленты и спора, закрыты; таймеры на паузе | «Сделка приостановлена администратором: {причина}» | то же | счёт не выставляется, пени не идут |
| **Отмена админом** → `cancelled_admin` | любой до `warranty` | админ (мошенничество, тест, дубль) | финал, обеим письмо с причиной | причина | причина | комиссия сторнируется проводкой |
| **Возврат** (будущее, Безопасная сделка) | `work`, `terminated`, спор | система/админ по решению спора | деньги этапа, лежащие на сделке, возвращаются клиенту | «Возврат {сумма}: {статус}» | — | комиссия с невыплаченных этапов не начисляется. **Сейчас (offsite)**: возврата денег через сайт нет; в журнале — «стороны отметили возврат {сумма}» для учёта базы комиссии |
| **Блокировка бригады** (флаг `brigade_blocked`) | любой | админ блокирует бригаду | текущие сделки **не обрываются автоматически**: клиенту письмо «бригада заблокирована по причине X; вы можете продолжить или расторгнуть с подбором новой»; новые запросы бригаде закрыты | баннер и выбор: «Продолжить с этой бригадой» / «Расторгнуть и подобрать другую» | только текущие сделки, лента, этапы; без ленты заказов | долг по комиссии сохраняется |
| **Долг по комиссии** (флаг на бригаде `debt`) | — | система | см. 2.7 | клиенту не показывается | баннер «Задолженность {сумма}, оплатите до …» | лестница: напоминания → лента закрыта → приостановка → блок |

### 2.5 Этап (`br_stages.status`)

| `plan` | По плану | — | при `signed`→`work` этап 1 становится `work` |
| `work` | В работе | бригада: фото по ходу | «Готов к приёмке» (нужно ≥ 3 фото и фото по пунктам чек-листа, где пункт требует фото) → `ready` |
| `ready` | Ждёт приёмки | клиент | «Принять этап» (все пункты чек-листа отмечены — уже в ветке) → `accepted`; «Вернуть на доработку» (≥1 замечание) → `returned` |
| `returned` | Доработка | бригада | закрыть все замечания с фото → снова `ready` |
| `accepted` | Принят | — | следующий этап → `work`; если последний → сделка `final_check` |
| `paid` | Принят и оплачен | обе стороны отметили оплату (или выплата из Безопасной сделки) | финал этапа |
| `disputed` | Спор | админ | решение спора → `accepted` / `returned` / `accepted_partial` (с суммой) |

**Старт этапа — кнопка «Начать работу» с фото «до»** (Авито): этап 1 и каждый этап со скрытыми работами нельзя перевести в `work` без
≥ 3 фото/видео объекта на момент старта; снимки хранятся на сервере LINEA (доказательство для споров), видны клиенту.

**Приёмка с таймером и правилом молчания** — параметр `brig_terms.stage_silence_days`, **предлагаемое значение — 5 рабочих дней** (Авито 1 сутки,
YouDo/Профи 3 дня, Upwork 14: ремонт — между ними, клиент не всегда на объекте, ему нужно время проверить по чек-листу; сутки для потребителя
в ремонте мало, 14 — бригада простаивает). Порядок:
`ready` → напоминание клиенту сразу, через 1 р.дн и **за 24 часа до срока** («завтра этап будет считаться принятым»); если клиент за
`stage_silence_days` не принял и не вернул с замечанием — система **сама оформляет односторонний акт** (ст. 753 п. 4 ГК: заказчик уклонился
от приёмки) → этап `accepted` с пометкой «принят по истечении срока, {дата}», клиенту письмо с актом; в течение `stage_silence_appeal_days`
(предложено 5 р.дн) клиент может открыть спор по этому этапу — тогда этап `disputed`. Явные недостатки после автоприёмки — по гарантии.
Исключения: этап в споре или сделка заморожена — таймер стоит; этап со скрытыми работами — `stage_silence_days_hidden` (предложено 3 р.дн, чтобы
не держать бригаду перед закрытием). Значение 0 = автоприёмка выключена (только ручная + админ). Срок и правило печатаются в договоре
(договор собирается из сделки, значение фиксируется в версии договора — менять для подписанной сделки нельзя).
Срыв срока бригадой: напоминание бригаде за 24 часа до плановой даты; после просрочки > `stage_overdue_cancel_days` (предложено 10 р.дн) клиент
может «Отказаться от этапа» одним нажатием → это предложение расторжения/допсоглашения (2.4), а не тихое удаление этапа.

Скрытые работы (электрика, сантехника, гидроизоляция, стяжка): чек-лист с пометкой `hidden=true` — «Готов к приёмке» требует фото до закрытия;
пока этап не принят, следующий этап «закрывающих» работ нельзя начать (кнопка «Начать» у бригады неактивна, причина подписана).

### 2.6 Оплаты (новое: `br_payments`)

Сейчас деньги идут **вне сайта**. Сайт ведёт **реестр отметок**, чтобы (1) знать «первые деньги» для комиссии, (2) видеть сальдо при споре
и расторжении, (3) завтра заменить отметки реальными платежами Безопасной сделки без переделки экранов.

```
br_payments: id, job_id, stage_id NULL, kind (advance|stage|extra|refund), amount_kop, due_at,
             method (offsite|safe_deal), status, declared_by (client|brigade|admin), declared_at,
             confirmed_by, confirmed_at, provider_deal_id NULL, provider_payment_id NULL, provider_payout_id NULL, note
status (offsite): planned → declared (одна сторона отметила) → confirmed (вторая подтвердила) | contested (вторая не согласна)
status (safe_deal): planned → funding → held (деньги у ЮKassa) → released (выплачено бригаде) | refunded | cancelled
```
- План платежей создаётся **из договора** (аванс % и оплата по этапам — поля договора), меняется только допсоглашением.
- Клиент: «Я передал аванс {сумма}» / «Я оплатил этап». Бригада: «Аванс получен» / «Оплата этапа получена». Любая из сторон может отметить
  первой, вторая подтверждает. **Первые деньги = первая отметка любой стороны** (не ждём подтверждения: иначе бригада тянет с подтверждением).
- Расхождение (клиент отметил, бригада 5 дней не подтверждает, или «не получал») → `contested` → сигнал админу + вопрос в ленте.
- Безопасная сделка: тот же реестр, `method=safe_deal`, кнопка у клиента «Внести {сумма}» вместо «Я передал», выплата после `accepted`.
  Переключатель — `brig_terms.payments = 'offsite' | 'safe_deal' | 'both'` (на сделку фиксируется при подписании договора: метод — часть договора).
  Код ЮKassa — отдельный модуль `lib/deals.php` (адаптер), экраны вызывают `brig_pay_*()`, которые знают оба метода.

### 2.7 Комиссия (новое: `br_ledger`)

- **Ставка** фиксируется в сделке при подписании договора: `br_jobs.fee_rate` (10 % или 5 % пилота). Пилот: бригада в списке
  `br_brigades.pilot = 1` (ставит админ, не больше 5) **и** у неё < 3 сделок, дошедших до первых денег. Пилотная ставка на сделку не меняется задним числом.
- **База** = сумма договора + Σ допсоглашений (без материалов, если в договоре материалы выделены как «закупает клиент»; если «материалы бригады» —
  в базу входят, ставка одна. Решение: база = сумма работ **и** материалов бригады — проще и честнее; пересмотр — через `brig_terms.fee_base`).
- **Проводки:**
  - `accrual` — при первых деньгах: `база × ставка`; создаётся счёт `br_invoices`, срок `invoiceDays` (10 дн).
  - `adjust+` / `adjust−` — при подписании допсоглашения: `Δбазы × ставка`; плюс — новый счёт (или строка в следующем счёте, если прошлый не оплачен);
    минус — кредит на балансе бригады (зачёт в следующие счета; деньгами — по заявлению, админ).
  - `termination` — при расторжении: база пересчитывается = Σ подтверждённых оплат бригаде; разница → `adjust−` (не ниже 0).
  - `payment` — админ отметил оплату счёта (позже — оплата счёта онлайн ЮKassa, тот же модуль, что проект).
  - `writeoff` — списание админом с причиной (спор решён в пользу клиента, мошенничество клиента и т.п.).
- **Баланс бригады** = Σ проводок. Долг = просроченные счета.
- **Лестница долга** (таймеры от `due_at`): +1 день — письмо; +7 — письмо + баннер; **+14 — лента новых запросов закрыта** (текущие сделки
  работают); +30 — статус `suspended`, письмо-претензия (шаблон), сигнал админу; +60 — `blocked` по решению админа. Новая регистрация
  с тем же ИНН невозможна (уникальный ИНН — в ветке); с другим ИНН, но тем же телефоном/почтой владельца/карточкой → сигнал `dup_owner`.
- **Безопасная сделка** (потом): `accrual` не выставляется счётом, а удерживается из каждой выплаты (`fee_mode = per_payout`) —
  `brig_terms.fee_mode = 'invoice' | 'per_payout'`. Экраны «Деньги» показывают одно и то же: начислено / оплачено / долг.
- **Статус LINEA:** пока нет ИП/ООО (`REQUISITES` пусто), проводки `accrual` создаются со статусом `deferred` — счёт **не выставляется**,
  бригаде показывается «Вознаграждение будет выставлено после регистрации ИП LINEA, ориентировочно {сумма}». Это закрывает запрет 422-ФЗ для
  самой LINEA (агентская деятельность в НПД запрещена — ст. 4 ч. 2 п. 8 [проверить у юриста]).

### 2.8 Сводная схема переходов сделки
```
выбор ──► contract ──► signing ──► signed ──(первые деньги: accrual)──► work ──► final_check ──► warranty ──► closed
   │          │            │          │                                   │            │
   │          └─declined_brigade / cancelled_client (без комиссии) ◄──────┘            │
   │                                  └──────── terminated (пересчёт по факту) ◄────────┘──► смена бригады (новая сделка)
   └─ флаги в любой точке: dispute · overdue · frozen · brigade_blocked · (на бригаде) debt
```
Каждый переход — одна функция в `lib/brig-deal.php` (`deal_transition($jobId, $to, $who, $why)`), которая проверяет таблицу разрешённых
переходов, пишет журнал сделки (`br_messages` с `who='system'`), журнал аудита (`br_audit`) и ставит уведомления в очередь.
Ни один эндпоинт не меняет `br_jobs.status` напрямую.

## 3. Кабинет клиента — ПРИОРИТЕТ 1 (уточнение Александра 01.11: «кабинет клиента и админ»)

Сейчас «кабинет» — это `order.html?t=<токен>`: одна страница одного заказа, вход только ссылкой. Нужен **настоящий кабинет**: вход по почте
кодом, все заказы клиента в одном месте, дизайн-проект и ремонт как два раздела одного объекта, документы, уведомления, профиль и согласия.

Принцип: **один экран — одно решение**. Вверху всегда «Сейчас от вас нужно» одной строкой и одна главная кнопка. Всё остальное — ниже
или во вкладках. На телефоне — одна колонка, главная кнопка липкая снизу. Слова — как у людей: «Ответить на вопросы», «Согласовать решение»,
«Оплатить», «Открыть альбом», «Принять этап».

### 3.0 Каркас кабинета

**Адрес и сборка.** Кабинет — одна страница-приложение `site/kabinet/index.html` (генератор: `tools/gen-kabinet-page.js` на каркасе
`site-shell.js`, noindex, вне sitemap; GitHub Pages — заглушка, как `brigady/`) + `site/js/kabinet.js` (разбит по разделам:
`kabinet-proekt.js`, `kabinet-remont.js`, `kabinet-docs.js`) ← API `server/api/client/*.php`. Маршруты по хэшу:
`#/` (объекты) · `#/o/<номер>` (объект) · `#/o/<номер>/proekt|voprosy|pravki|remont|sdelka|etap/<id>|docs` · `#/uvedomleniya` · `#/profil`.

**Вход — по почте кодом, без пароля.**
1. «Ваша почта» → «Получить код». Ответ всегда одинаковый («Если почта есть в заказах — код отправлен»), чтобы не раскрывать, есть ли клиент.
2. Код 6 цифр, живёт 10 минут, 5 попыток, не больше 5 кодов в час на адрес и 20 в час с IP. В базе только sha256 кода (`account_tokens`, purpose `login`).
3. Сессия `linea_acc` (общая с бригадами, `role=client`), 30 дней «запомнить это устройство», idle 7 дней; список устройств и «Выйти везде» — в профиле.
4. Аккаунт клиента создаётся **автоматически** при первом брифе (почта из брифа, `accounts.role='client'`, без пароля). Все заказы с этой
   почтой привязываются к аккаунту (`orders.account_id`, новая колонка, заполняется миграцией по `orders.email`, нижний регистр).
5. Заказ без почты (бриф прислан архивом в WhatsApp) — привязывается, когда клиент первый раз заходит по старой ссылке с токеном и вводит
   почту (подтверждение кодом).
6. **Значимые действия** требуют входа по коду не старше 12 часов (иначе — «Подтвердите кодом из письма» поверх экрана, без потери введённого):
   оплата, согласование решений и изменений проекта, выбор бригады, подписи ПЭП, отметки оплат, приёмка этапа, спор, отзыв, отзыв согласия,
   удаление данных.

**Старые ссылки с токеном продолжают работать и ведут в кабинет.**
- `order.html?t=<токен>` → сервер (`api/client/link.php?t=`) проверяет токен заказа и:
  - если у заказа есть аккаунт и в браузере уже есть сессия этого аккаунта → редирект `kabinet/#/o/<номер>`;
  - иначе выдаёт **гостевую сессию заказа** (`role=client_guest`, привязана к одному заказу, 12 часов, cookie httponly) и открывает тот же
    кабинет в режиме «один заказ»: всё **видно**, значимые действия — «Подтвердите почту кодом» (код на почту заказа; почты нет — ввести и подтвердить).
  - токен убирается из адресной строки сразу (`history.replaceState`), Referrer-Policy no-referrer — как сейчас.
- `order.html` как страница остаётся тонким переходником (на GitHub Pages и для старых закладок), сама ничего не показывает, кроме «Открываем кабинет…».
- Ссылки в письмах — только `kabinet/#/o/<номер>` без токена (вход по коду). Токен остаётся для уже разосланных писем и для `review.html?t=`.
- Перевыпуск токена (кнопка в админке, п. 5.2) делает старую ссылку недействительной; кабинет по почте продолжает работать.

**Шапка кабинета:** логотип · «Мои объекты» · колокольчик (число непрочитанных) · аватар-меню (Профиль, Документы, Выйти).
Телефон: нижняя панель из 4 иконок — **Объекты · Документы · Уведомления · Профиль**.

### 3.1 Экран «Мои объекты» (`#/`)
- Карточка на каждый заказ: вид («Дизайн-проект квартиры»), объект обезличенно («Квартира 78,9 м², Химки»), номер LN-…, **шаг** полосой
  (Бриф → Оплата → Работа над проектом → Первый вариант → Вопросы и правки → Финальный альбом → Ремонт), и строка «Сейчас от вас нужно» с кнопкой.
- Порядок: сначала те, где нужно действие клиента, затем активные, затем архив (свёрнут).
- Пусто: «Здесь будут ваши проекты. Заполните бриф — это около 5 минут» + кнопка «Заполнить бриф» (фраза о времени — из `TERMS`).
- Кнопка «Новый проект» → `brief.html` с подставленными контактами (бриф после входа не спрашивает почту и телефон заново).

### 3.2 Объект — раздел «Дизайн-проект» (`#/o/<номер>/proekt`)

Вкладки объекта: **Проект · Вопросы · Правки · Ремонт · Документы** (на телефоне — горизонтальная лента вкладок, активная прокручивается в видимую зону).

**3.2.1 Главная проекта.** Блок «Сейчас от вас нужно» + полоса шагов + плитки:

| Плитка | Что внутри | Пустое состояние |
|---|---|---|

**3.2.2 Вопросы к заказчику (К-N) и подписи решений (`#/o/<номер>/voprosy`).**
Источник — реестр альбома GOST-DRAFT: открытые вопросы `К-N`, конфликты `Кф-N`, изменения `ИЗ-N`, предложения проектировщика (`proposed: true`, знак «**»).
Движок при выпуске кладёт рядом с листами `registry.json` (`sync-gost-releases.sh` переносит его в `linea-private/orders/<номер>/releases/<версия>/`).

- Фильтры-вкладки: **Вопросы** (К-N) · **Решения** (предложения «**» и ИЗ-N) · **Отвечено**.
- Карточка вопроса: номер «К-7», простой текст вопроса (поле `client_text` в реестре — движок пишет человеческую формулировку, не служебную),
  **миниатюра листа с меткой места** (клик — лист целиком в просмотрщике `review.html` с подсветкой), варианты ответа кнопками, если движок их дал
  («Да, оставить стену» / «Нет, сносить» / «Не знаю — уточню на обмере»), поле «Свой ответ» (текст, голос → текст), фото («сфотографируйте щиток»).
  Кнопка «Ответить». Ответ можно изменить, пока не вышла следующая версия.
- Карточка решения: что предлагаем, почему (`why`), на каких листах, влияние на смету («+12 400 ₽ к ремонту» — если движок посчитал),
  кнопки **«Согласовать»** / **«Не согласен — предложить своё»** (текст). «Согласовать» = подпись решения: ПЭП-код не нужен, достаточно
  свежего входа по коду; записывается `decidedBy=client:<id>`, `decidedOn`, IP, редакция листа (sha256 `registry.json` версии) — тот же журнал подписей,
  что у договоров ремонта (`br_contracts` → общая таблица подписей `signatures`, см. 3.6).
- «Ответить на всё сразу» — режим мастера по одному вопросу на экран (телефон) с прогрессом «5 из 7».
- Ответы уходят в `linea-private/orders/<номер>/answers.json` (+ событие заказа, уведомление админу). Студия переносит их в `project.json`
  движка (`tools/answers-to-project.mjs` — в GOST-DRAFT, вне этого репо) и выпускает новую версию; вопрос в новой версии закрыт → карточка
  «Отвечено, учтено в версии 2».
- Пусто: «Вопросов к вам нет — всё понятно из брифа».
- «Сейчас нужно»: «Ответьте на 7 вопросов — без ответов финальный альбом не выпустить» (если есть блокирующие: `blocker: true` в реестре — сверху, красная метка «Нужно для финала»).

**3.2.3 Правки по листам (`#/o/<номер>/pravki`).**
- Кнопка «Отметить правку на листе» → `review.html?o=<номер>` (в кабинете — по сессии, без токена; review.js берёт заказ из сессии).
- Список отправленных правок R-…: дата, число меток, статус («Получены» → «В работе» → «Учтены в версии N» / «Не приняты — почему»),
  у каждой метки — миниатюра листа и ответ студии.
- Число кругов правок: «Использовано 1 из 3» (`ROUNDS` из `TERMS`; null — строка скрыта). Круг = одна отправка; после последнего — «Дополнительный
  круг правок — {цена}» (если задана) кнопкой оплаты.
- Пусто: «Правок пока нет. Откройте любой лист и нажмите на место, которое хотите изменить».

### 3.7 Уведомления (`#/uvedomleniya`)
- Лента событий по всем объектам (новое — жирным), «Отметить всё прочитанным». Клик ведёт к месту (вопрос, этап, договор).
- Настройки: по группам **Проект · Вопросы и правки · Ремонт · Деньги** × каналы **почта / Telegram** (Telegram — когда `tg_enabled`, привязка
  кодом через бота). Обязательные (оплата, подписи, спор, удаление данных) — без выключателя, с подписью «нельзя отключить: это юридически значимо».
- «Сводка вместо каждого письма»: сразу / раз в день (для сообщений ленты и фото этапов).
- Пусто: «Новостей нет».

### 3.8 Профиль и согласия (`#/profil`)
- **Контакты:** имя, почта (смена — кодом на старую и новую), телефон, как обращаться.
- **Устройства:** где выполнен вход, «Выйти на этом устройстве», «Выйти везде».
- **Доверенные лица:** пригласить по почте наблюдателя (видит объект, пишет в ленту, не подписывает) — этап 2.
- **Согласия** — список с редакцией и датой: обработка ПДн (`LEGAL_ED`), показ проекта в портфолио (можно снять), передача проекта бригадам
  (на объект), передача контактов бригаде (на сделку), рассылка новостей (если появится, отдельно, выкл. по умолчанию). У каждого «Отозвать»:
  - портфолио — сразу, проект снимается с сайта при следующей пересборке (админу задача «снять с портфолио»);
  - передача проекта бригадам — пока сделки нет: запрос закрывается, бригадам пакет недоступен; после подписания договора — нельзя (договор исполняется);
  - **ПДн целиком** — то же, что «Удалить мои данные».
- **Удалить мои данные (152-ФЗ):** экран объясняет простыми словами: что удалим (контакты, бриф, фото, переписку), что обязаны хранить и сколько
  (договоры, чеки, акты, подписи — до 5 лет по закону о бухучёте и для защиты прав сторон, доступ к ним закрыт), что будет с проектом (альбом
  обезличивается: адрес и ФИО со штампа — при перевыпуске). Если идёт оплаченная работа или ремонтная сделка — «Удалить можно после завершения;
  сейчас можем остановить обработку для новых целей» (кнопка «Отозвать согласие на всё, кроме исполнения договора»). Подтверждение кодом →
  заявка `pd_requests` → срок исполнения **10 рабочих дней** (ст. 21 ч. 5 152-ФЗ — 30 дней с отзыва, ставим себе короче) → письмо «выполнено» с перечнем.
  Админ видит заявку в «Требует действия» с таймером.
- **Выгрузить мои данные** (ст. 14 152-ФЗ — право на сведения): архив ZIP с брифом, ответами, документами — по коду, готовится до 1 дня.

### 3.9 Мобильная версия (клиент)
- Ширина 375: одна колонка, без горизонтальной прокрутки страницы (ошибка 1 из `testy-sait` — таблицы только внутри своих контейнеров с `min-width:0`).
- Главная кнопка — липкая снизу, высота ≥ 48 px; вторичные действия — в меню «⋯».
- Сравнение — карточки свайпом + «Разница по разделам» (не таблица на 54 строки).
- Приёмка — пошагово, по одному пункту на экран, камера открывается из пункта (`<input type=file accept=image/* capture=environment>`).
- Код из письма: поле `inputmode=numeric autocomplete=one-time-code`.
- Офлайн: отметки и фото, сделанные без сети, ставятся в очередь (localStorage) и отправляются при появлении сети, с пометкой «отправится, когда будет связь».

## 4. Кабинет бригады — равноправная часть (уточнение Александра: «кабинет клиента, кабинет бригад, админ и сам сайт»)

Сейчас `/brigada/` (`site/js/brigada.js`, 4 вкладки: профиль, лента, объекты, финансы; вход паролем). Целевой — такой же по уровню, как кабинет
клиента: те же каркас, вход кодом, «Сейчас от вас нужно», лента сделки, документы, уведомления, профиль и согласия.

### 4.0 Каркас кабинета бригады
- **Адрес:** `site/brigada/index.html` остаётся (генератор `gen-brigady-pages.js`), JS разбивается: `brigada.js` (каркас/маршруты) +
  `brigada-lenta.js`, `brigada-obekty.js`, `brigada-dengi.js`, `brigada-profil.js`. Маршруты: `#/` (главная) · `#/zakazy` · `#/zakaz/<id>` ·
  `#/obekty` · `#/obekt/<id>/{glavnaya|lenta|dogovor|etapy|etap/<id>|oplaty|listy|docs|spor}` · `#/listy` · `#/dengi` · `#/profil` ·
  `#/komanda` · `#/reiting` · `#/uvedomleniya`.
- **Вход — тот же единый вход кодом на почту** (раздел 4А). Пароль сохраняется как запасной способ для уже созданных аккаунтов (выключатель
  `acc_password_login`), новым — не спрашивается. Значимые действия (отправка предложения, подписи, отметки оплат, «сдать этап», спор)
  требуют входа по коду не старше 12 часов.
- **Навигация:** десктоп — левое меню; телефон — нижняя панель из 5 иконок **Главная · Заказы · Объекты · Деньги · Ещё** (в «Ещё»: Листы,
  Рейтинг, Команда, Профиль, Уведомления, Документы).
- Роль внутри бригады (1.2) определяет, какие пункты видны: бригадир не видит «Деньги» и «Команду», сотрудник — только свои объекты и листы.

### 4.0а Главная бригады (`#/`)
- «Сейчас от вас нужно» — список (не одна строка, у бригады параллельно несколько объектов), по срочности:

| Ситуация | Строка | Кнопка |
|---|---|---|
| анкета `draft` | «Заполните анкету: не хватает {что}» (портфолио 1 из 3, ИНН…) | «Заполнить» |
| `review` | «Анкета на проверке. Видеозвонок — {дата/«мы напишем»}» | — |
| новый запрос в районе, срок близко | «Новый заказ: квартира 78 м², Химки — ответ до {дата}» | «Посмотреть» |
| вопрос клиента по предложению | «Клиент спросил по объекту …» | «Ответить» |
| вас выбрали | «Вас выбрали на объекте … Проверьте договор» | «К договору» |
| договор ждёт подписи владельца | «Подпишите договор по объекту …» | «Подписать» |
| клиент отметил оплату | «Клиент отметил аванс 150 000 ₽ — подтвердите» | «Подтвердить» / «Не получал» |
| этап возвращён | «Этап «Электрика» вернули: 2 замечания» | «Открыть замечания» |
| плановая дата этапа прошла | «Этап «Стяжка» просрочен на 3 дня — сдайте или предложите новый срок» | «Сдать этап» / «Перенести срок» |
| лист готов / вопрос по листу | «Лист готов: раскладка плитки, санузел» | «Открыть лист» |
| счёт на вознаграждение | «Счёт LB-… на 95 144 ₽ — до {дата}» | «Оплатить» |
| спор | «Клиент открыл спор по объекту … — ответ до {дата}» | «Ответить» |
| пусто | «Всё сделано. Новые заказы придут на почту» | — |

- Ниже — плитки-цифры: «Заказы в ленте: 3», «Объекты в работе: 2», «К оплате площадке: 0 ₽», «Рейтинг 4,8 (12)».

### 4.0б Документы бригады
Агентский договор/правила площадки (редакции, дата и IP принятия), договоры подряда и допсоглашения, акты этапов, итоговые акты, счета LINEA
и акты оказанных услуг площадки (для ИП/ООО — ежемесячно), листы по запросу (PDF), журналы подписей. Скачать по объекту архивом.
Удаление данных бригады (владельца) — как у клиента (3.8), с той разницей, что при долге по вознаграждению аккаунт не удаляется до расчёта,
а рейтинг и отзывы клиентов остаются обезличенно («бригада удалила профиль»).

Разделы ниже — содержимое вкладок.

### 4.1 Профиль и проверка
- Анкета как сейчас (форма, ИНН с контрольной суммой, специализации, районы, состав, опыт, гарантия, портфолио ≥ 3 объекта до/после).
- **Облегчённый вход** (из ревью продукта): «Лист ожидания» — телефон, район, специализация — без анкеты, пока заказов мало; анкета — по приглашению
  админа «есть заказ в вашем районе». Флаг `brig_terms.waitlist = true`.
- **Форма деятельности** и что из неё следует:

| Форма | Допуск | Что показываем бригаде | Проверка |
|---|---|---|---|
| ИП | да | — | ЕГРИП: статус «действующий», ОКВЭД 43.* желательно; выписка по API ФНС (egrul.nalog.ru) — кнопка в админке |
| ООО | да | подписант и основание | ЕГРЮЛ: действующее, не в ликвидации, руководитель |
| Самозанятый (НПД) | да, **с ограничениями** | (1) «Как самозанятый вы не можете нанимать работников по трудовому договору: в бригаде каждый мастер — сам самозанятый или ИП, либо вы работаете один»; (2) счётчик лимита дохода НПД 2,4 млн ₽/год: при сумме договора, которая выведет за лимит, — предупреждение при отправке предложения; (3) чек клиенту — через «Мой налог» на каждую полученную оплату (напоминание после отметки оплаты) | статус НПД по API ФНС (уже есть кнопка `b_npd`); повтор раз в месяц cron-ом — снят с учёта → приостановка ленты |

  **Про 422-ФЗ.** Запрет агентской деятельности в НПД касается **того, кто получает вознаграждение** (LINEA), а не бригады, которая его платит.
  Бригада на НПД вправе оплатить услугу площадки как расход [проверить у юриста]. Поэтому: бригады-НПД допускаются; LINEA принимает комиссию
  только будучи ИП/ООО (п. 2.7 `deferred`). Сделки бригады-НПД с суммой > 2,4 млн ₽ — запрет подачи предложения (сервер), текст:
  «Сумма больше лимита дохода самозанятого. Чтобы подать предложение, нужен статус ИП».
- Смена формы (НПД → ИП) — через админа: новый ИНН (ИНН физлица у ИП тот же — тогда просто смена `legal`; ООО — новая бригада с переносом
  портфолио и рейтинга по решению админа, старая архивируется).
- Статусы анкеты: `draft → review → active → suspended → blocked`, плюс `archived` (бригада сама закрыла аккаунт). Причина — всегда текстом.

### 4.2 Портфолио
Объекты «до/после», район, площадь, год, виды работ. Объекты, сделанные **через LINEA**, добавляются автоматически после `warranty` (с фото
этапов, с согласия клиента на публикацию — галочка в отзыве) и помечаются «Сделано через LINEA» — это и есть растущий актив бригады на платформе.
Фильтр контактов на подписи и описании (в ветке).

### 4.3 Лента заказов
- Карточка: объект обезличенно («Квартира 78,9 м², 3 комнаты, Химки»), виды работ, старт, срок ответа, «сколько бригад приглашено» (число, без имён),
  ориентир бюджета клиента (если дал).
- Открытие: пакет — позиции сметы по разделам, ведомости xlsx, листы альбома (просмотр; скачивание — водяной знак «бригада {№}, запрос {№}»).
- Действия: «Подать предложение» · «Задать вопрос» (в ленту запроса; ответ админа/клиента виден всем приглашённым — общий FAQ запроса, без контактов) · «Не беру».
- Пустое: «Новых заказов в ваших районах нет. Добавьте районы или специализации — заказов станет больше» + ссылка в профиль.
- Ограничения: долг > 14 дн или `suspended` — лента скрыта с объяснением и кнопкой «Оплатить».

### 4.4 Предложение по строкам сметы
- Как сейчас: цена за единицу или «не делаем», материалы, график этапов, старт, гарантия, комментарий.
- **Добавить режим «по разделам»** (из ревью): цена за раздел целиком (демонтаж, электрика, сантехника…) — позиции внутри раздела не заполняются;
  клиент в сравнении видит раздел целиком. Сервер считает итог в обоих режимах.
- **Аванс и план оплат** — поля предложения (аванс %, оплата по этапам: после приёмки каждого) → из них собирается договор.
- Черновик сохраняется; бригадир может готовить черновик, отправляет только владелец.
- Подсказки: «у 3 из 5 бригад в этом районе электрика дороже на 12 %» — **нет** (не раскрываем чужие цены). Есть только «рыночный ориентир LINEA»
  по разделу, если накоплено ≥ 5 сделок (этап 2).
- Отправка → «Предложение отправлено. Править можно до {срок}».

### 4.5 Договор
Тот же экран, что у клиента (К9/К10): черновик → реквизиты бригады (из анкеты, подставлены) → «Отправить на подпись» → код → ждём клиента.
Владелец видит кнопку «Подписать», бригадир — «Попросить владельца подписать» (уведомление владельцу).

### 4.6 Объекты (сделки) и этапы с фото
- Список объектов: шаг, что нужно от бригады, просрочки красным.
- Карточка объекта: Главная («Сейчас: …»), Лента, Договор, Этапы, Оплаты, Листы, Документы, Спор — зеркально клиенту.
- Этап: «Начать» (дата факта), фото по ходу (с подписью и привязкой к пункту чек-листа), «Сдать этап» → `ready`. Замечания: каждое закрывается фото.
- Камера с телефона, пережатие на клиенте до 1600 px перед загрузкой (экономия трафика на объекте), очередь загрузки при плохой связи.

### 4.7 Листы по запросу (голос/текст → лист)
- Кнопка «Нужен лист» доступна только при `signed`/`work`/`final_check` (в ветке).
- Форма: помещение (список из проекта), стена A–D (картинкой плана, не буквами), «что нужно» — текст или «Надиктовать» (Web Speech → текст,
  правка перед отправкой); запись голоса прикладывается к тексту (без текста отказ — как сейчас).
- Счётчик «использовано 4 из 15 на этот объект» (`brig_terms.sheets_free_limit = 15`). На 15-м — «Лимит исчерпан. Попросите администратора
  увеличить или дождитесь платных листов» (`sheets_outside_paid=false` — кнопки оплаты нет).
- Статусы: «Принят» → «Делаем» → «Готов» (PDF) / «Вопрос» (ответить текстом) / «Не получилось» (причина). Срок-ориентир — из воркера.
- Каждый лист: номер «объект/бригада/№», редакция проекта, виден клиенту (К14).

### 4.8 Деньги
- Сводка: **Начислено · Оплачено · К оплате · Просрочено** (+ «Отложено до регистрации ИП LINEA», пока `deferred`).
- Таблица по объектам: сумма договора, допсоглашения, ставка (10 % / 5 % «пилот»), комиссия, счёт, срок, статус.
- Счёт: PDF с реквизитами LINEA, назначение, «Оплатить» (сейчас — реквизиты для перевода; позже — онлайн ЮKassa тем же `pay.php`-модулем).
- История проводок с пояснением простыми словами: «Начислено при первом платеже клиента 12.11», «Доплата по допсоглашению №2», «Уменьшено при расторжении».
- Пилот: «Вы в пилоте: ещё 2 сделки по ставке 5 %».
- Объяснение «Когда я плачу?» одним абзацем из `BRIG_TERMS.feeLine`.

### 4.9 Рейтинг
- Показатели: средняя оценка (только отзывы по сделкам, дошедшим до `warranty`), число сделок через LINEA, доля этапов, принятых с первого раза,
  среднее время ответа на запрос, просрочки, споры (проиграно).
- Формула ранжирования в ленте/подборе — публичная (правила площадки): рейтинг, сделки через LINEA, время ответа, район. Платного поднятия нет.
- Отзыв: бригада может **ответить** один раз (публично).

### 4.10 Команда
Пригласить бригадира/сотрудника по почте, роль, объекты, удалить. Удалённый теряет доступ сразу; его фото и сообщения остаются в сделке с подписью.

### 4.11 Уведомления
Настройка по группам (Заказы, Объекты, Деньги, Листы) × канал (почта, Telegram). Обязательные (подпись, долг, спор, блокировка) отключить нельзя.

### 4.12 Мобильная версия (бригада)
Бригада живёт в телефоне на объекте — это основной экран, десктоп вторичен.
- Нижняя панель, крупные цели (≥ 48 px), без горизонтальной прокрутки; таблица предложения — карточками по позиции (уже так) и по разделу.
- «Сдать этап» — мастер: пункты чек-листа по одному, камера из пункта, затем «Отправить клиенту».
- Фото пережимаются в браузере до 1600 px, очередь загрузки при слабой связи с индикатором «загружено 7 из 12».
- «Нужен лист» — кнопка на карточке объекта и на этапе; диктовка крупной кнопкой микрофона.
- Код из письма — `autocomplete=one-time-code`; Telegram-бот (флаг) дублирует «Сейчас нужно» и присылает код подтверждения действий (не ПЭП).

## 4А. Как связаны части: сайт · кабинет клиента · кабинет бригады · админка

Четыре равноправные части над **одной базой** (`lib/db.php`, MySQL на Beget) и одним набором правил (`brig_terms()` / `TERMS`).

```
        Сайт (публичный, статика + katalog.php)
        бриф ─► заказ        каталог бригад ◄─ база        тексты условий ◄─ site-shell.js (TERMS, BRIG_TERMS)
           │                       ▲                                ▲
           ▼                       │                                │
  Кабинет клиента ◄──── общая лента сделки, договор, этапы ────► Кабинет бригады
           ▲   ▲                                                   ▲
           │   └────────────── единый вход кодом на почту ─────────┘
           └───────────────────────── Админка (всё видит, всем управляет, журнал) ─────────┘
```

### 4А.1 Единый вход
- Одна страница входа `site/vhod/index.html` (+ кнопка «Войти» в шапке сайта из `site-shell.js`): почта → код → сервер находит **все роли** этой почты
  (`accounts` с `role in (client, brigade_owner, brigade_member, admin, moderator)`; `UNIQUE(role,email)` уже есть — роли живут отдельными записями,
  объединяются по почте).
- Одна роль → сразу в свой кабинет. Несколько (клиент LINEA, который ещё и бригадир; Александр как админ и тестовый клиент) → экран
  **«Куда войти?»** с карточками «Мои проекты и ремонт» / «Бригада «…»» / «Админка». Выбор запоминается на устройстве; переключатель ролей — в
  меню аватара каждого кабинета без повторного кода (сессия одна, `active_role` в сессии, права проверяются по активной роли).
- **Админка — вход кодом + второй фактор** (код в Telegram или TOTP) и только с проверенной почты из config; прямой путь `api/admin.php` с паролем
  остаётся аварийным (выключатель `admin_password_login`).
- Гостевая сессия по старой ссылке с токеном (3.0) — частный случай: роль `client_guest` на один заказ.
- Один человек не может быть клиентом и бригадой **в одной сделке** (сервер: почта/телефон клиента ≠ почта/телефон владельца и членов бригады;
  совпадение → сигнал и запрет выбора).

### 4А.2 Общая лента сделки
- Одна лента `br_messages` на сделку (в ветке) — **один и тот же** поток для клиента, бригады (владелец, бригадир, сотрудники по настройке) и админа.
- В ленту автоматически пишутся системные события: выбор, версии договора, подписи, допсоглашения, отметки оплат, начало/сдача/приёмка этапов,
  замечания, листы по запросу, спор, решения админа — с одинаковым текстом для обеих сторон (`deal_transition()` → одна запись).
- До подписания — фильтр контактов (в ветке); после — свободно, но фильтр «уйти с площадки» (фразы, п. 6 №24) продолжает давать сигналы.
- Сообщение от админа — с меткой «LINEA», видно обеим сторонам; приватная заметка админа — только в админке (`br_admin_notes`).
- Лента дизайн-проекта (клиент ↔ студия) — **отдельная** (`events` заказа с признаком `visible_to_client`), бригада её не видит.
- Вложения в ленте — фото и PDF (PDF — только `attachment`), через `br_files`, с теми же правами.

### 4А.3 Что из админки управляет сайтом

| Что на сайте | Источник | Как обновляется |
|---|---|---|
| Каталог `/brigady/`, карточки `/brigady/<slug>/` | база: статус `active`, демо `demo=1` (только «образец», пока нет настоящих), значки проверки, рейтинг, «сделок через LINEA» | **сразу** — `katalog.php` рендерит из базы; действия админки (допуск, блок, скрытие отзыва) видны на сайте мгновенно; `sitemap` бригад — тоже из базы |
| Тексты условий (ставка, когда открываются контакты, листы, гарантия) на `/brigadam/`, `/remont/`, в правилах и договорах | `site-shell.js → BRIG_TERMS` (страницы) + `boot.php → BRIG_TERMS_DEFAULT` / `config.php brig_terms` (сервер) | **не мгновенно**: правка в админке (5.13) пишет `brig_terms` в config/базу и ставит задачу «пересобрать страницы»; в админке висит красная плашка «Условия на сайте устарели: ставка на сайте 10 %, на сервере 12 %», пока генераторы не прогнаны и не выложены. ## 5. Админка — ПРИОРИТЕТ 1 вместе с кабинетом клиента

Сейчас: `admin.php` (заказы проектов) + `admin-brigady.php` (вкладки). Целевая структура — **одна админка с левым меню**
(`site`-независимая, `server/api/admin/*.php` + `admin.js`), общий вход (4А.1). Меню:
**Дашборд · Заказы проектов · Вопросы и правки · Выпуски альбомов · Клиенты · Ремонт: запросы · Сделки · Бригады · Договоры и подписи ·
Споры · Деньги (оплаты проектов, комиссии и счета) · Листы по запросу · Отзывы · Сигналы обхода · Заявки по ПДн · Уведомления (исходящие) ·
Журнал · Экспорт · Настройки.**

### 5.1 Дашборд (первый экран)
- **Деньги:** выручка проектов за 7/30 дней (оплачено), комиссия: начислено / оплачено / просрочено / отложено (`deferred`); сумма договоров в работе.
- **Воронка ремонта (30 дней):** проекты выданы → подбор открыт → предложения ≥1 → выбор → подписан → первые деньги → завершено. Конверсия по шагам и
  где «застряло» сейчас (кликабельно в список).
- **Требует действия** (главный блок, сортировка по сроку): анкеты на проверке; запросы `new`/`empty`; сделки без подписи > 5 дн; этапы без приёмки > 5 р.дн;
  оплаты `contested`; споры с истекающим сроком; листы «вопрос» без ответа; счета просрочены; сигналы обхода новые.
- **Сигналы обхода:** счётчик новых по типам (контакты в тексте, отказ после выбора, `sign_timeout`, `no_money_14d`, `dup_owner`, расхождение оплат).
- **Споры:** открытые, срок решения.
- **Долги:** топ бригад по просрочке.
- На телефоне: только «Требует действия» и цифры денег.

Дашборд — дополнение по проектам (верх экрана, до ремонта):
- **Проекты:** новые брифы за 7 дней, ждут суммы, ждут оплаты (сумма в ожидании), оплачены в работе, просрочены по сроку первого варианта,
  ждут ответов клиента (К-N), правки не разобраны, выданы за месяц. Каждая цифра — ссылка на отфильтрованный список.
- **Деньги проектов:** оплачено за 7/30 дней, возвраты, платежи-«сироты» (платёж на отменённый/уже оплаченный заказ — из ветки безопасности).
- **Требует действия** (общий список с ремонтом): новый бриф без суммы > 4 ч рабочего времени; не оплачен > 1/3/7 дней (напомнить — кнопкой);
  оплачен, но не создана папка клиента; срок первого варианта через 24 ч; клиент ответил на вопросы → выпустить версию; новые правки R-…;
  заявки по ПДн с таймером.

тест. Фильтры: статус, «ждёт студию», «просрочен», вид, период, поиск по номеру/почте/телефону. На телефоне — карточки.

### 5.2а Клиенты
Список аккаунтов клиентов: почта, имя, объекты, последняя активность, согласия (ПДн, портфолио), заявки по ПДн. Карточка — все заказы и сделки,
устройства (завершить сессии), история входов, «объединить аккаунты» (две почты одного человека — по заявлению, с журналом).

### 5.2б Заявки по ПДн (152-ФЗ)
Очередь `pd_requests`: вид (удаление, отзыв согласия, выгрузка сведений, исправление), клиент/бригада, дата, **срок** (10 рабочих дней по нашему
регламенту, 30 по закону — красным за 3 дня), что мешает (активная сделка/долг). Действия: «Выполнить» (скрипт обезличивания — показывает, что
удалится и что останется по сроку хранения), «Отказать частично» (обязательная причина со ссылкой на основание), журнал уничтожения.

### 5.2в Исходящие уведомления
Очередь `br_outbox`/`notify`: что ушло, кому (роль, без адреса в списке — адрес по клику), канал, статус, ошибка. «Отправить повторно».
Плашка, если письма выключены (`notify_enabled`/`brig_mail_enabled` = false) — «Письма не уходят: клиенты ничего не получают».

### 5.3 Сделки
Список с фильтрами (статус, флаг, бригада, район, просрочка). Карточка сделки — всё, что видят стороны, + служебное: журнал полностью, IP подписей,
сигналы по сделке, проводки комиссии. Действия админа (каждое с причиной): заморозить/разморозить, отменить, сменить статус этапа по решению спора,
продлить срок подписи/ответа, «Открыть контакты» (только при `dispute`/жалобе, журнал), написать в ленту от имени LINEA.

### 5.4 Бригады
Очередь модерации (анкета, портфолио, ИНН: контрольная сумма, кнопки ФНС НПД / ЕГРЮЛ-ЕГРИП / Прозрачный бизнес / Федресурс (банкротство) / ФССП (долги)),
отметки «ИНН проверен», «видеозвонок», «пилот». Действия: допустить, вернуть на доработку (с текстом), **предупредить** (пункт правил + цитата
нарушения; счётчик лестницы `warn_ladder` виден бригаде в профиле), приостановить (срок), заблокировать (причина из списка правил + текст,
уведомление с порядком обжалования; начатые сделки бригада доводит — `block_finish_current`), разблокировать, рассмотреть обжалование (очередь).
Жалобы на бригаду от конкурентов — только с доказательствами, идут как сигнал, автоматических мер не вызывают. Профиль бригады: сделки, рейтинг, деньги, сигналы, члены команды,
связанные аккаунты (совпадения телефона/почты/IP регистрации).

### 5.5 Договоры и подписи
Реестр: сделка, версия, sha256, кто подписал, время (МСК и UTC), IP, почта, код (только факт, не значение), допсоглашения. Проверка целостности
«пересчитать sha256 по сохранённому PDF» — кнопка. Выгрузка пакета доказательств по сделке (ZIP: PDF версий, журнал подписей, лента, фото этапов) — для суда.

### 5.6 Споры / арбитраж
Очередь со сроками. Регламент (показывать в карточке спора):
1. Открытие: тема из списка (качество, срок, деньги, объём, поведение, другое), суть, доказательства. Вторая сторона — `dispute_reply_days`
   (5 р.дн) на ответ; таймер виден обеим; молчание — админ решает по материалам заявителя.
2. Модератор/админ собирает доказательства (фото «до» и этапов, чек-листы, лента, листы) — до 5 рабочих дней; можно запросить выезд практика (платно, решение админа).
2а. **Предложение решения** — сторонам `dispute_proposal_days` (2 р.дн) согласиться кнопкой; согласились — исполняется; нет — окончательное решение.
3. Решение — до 10 рабочих дней от открытия: «этап принят», «этап на доработку с перечнем», «принят частично на сумму X», «расторжение рекомендовано»,
   «комиссия списана/сохранена». Решение платформы — **рекомендация** для offsite-денег (суд остаётся у сторон); в Безопасной сделке — основание
   для выплаты/возврата (прописать в оферте Безопасной сделки).
4. Шаблоны решений, обязательное обоснование, оба получают письмо.

### 5.7 Комиссии и счета
Проводки по бригадам, счета (выставить/переотправить/отметить оплату с основанием: № платёжки, дата), списание (только админ, причина), кредит/зачёт,
акт выполненных услуг за месяц (PDF, для бригад ИП/ООО), CSV. Пока `deferred` — экран показывает «отложено» и кнопку «Выставить все отложенные»
(станет активной, когда заполнены `REQUISITES`).

### 5.8 Листы по запросу (очередь)
Статусы, возраст, бригада/объект, текст, вопрос/ответ; действия: переназначить в очередь, ответить на вопрос от LINEA, отклонить с причиной,
увеличить лимит объекта (+5, с причиной). Алерт: заявка без движения > 24 ч (воркер лежит).

### 5.9 Отзывы
Как сейчас (скрыть только по 5 причинам правил).

### 5.10 Сигналы обхода
В ветке; дополнить разметкой «ложный / подтверждён / меры приняты», связью с бригадой и сделкой, и **сводкой по бригаде** (доля «выбрана → первые деньги»).

### 5.11 Журнал действий администратора
`br_audit` (есть) — фильтр «только админ/модератор», поля: кто, что, объект, причина, IP. Нельзя удалить или править (только добавлять).
Отдельно отмечать «просмотр контактов» и «экспорт ПДн».

### 5.12 Экспорт
CSV: сделки, проводки, счета, бригады (без паспортных данных), сигналы. Экспорт с ПДн клиентов — только админ, с причиной, с отметкой в журнале
и вторым фактором.

### 5.13 Настройки `brig_terms`
Форма над `config.php → brig_terms` (или таблица `settings` в базе, чтобы не править файл по SSH): ставка, пилотная ставка и лимиты пилота,
лимит листов, листы вне сделки (вкл/цена), сроки (ответ бригад, выбор, подпись, приёмка, счёт), лестница долга, способ оплат (`offsite/safe_deal`),
`fee_mode`, Telegram вкл/выкл, производственный календарь (праздники года). Изменение ставки **не трогает подписанные сделки** (ставка зафиксирована
в сделке), применяется к новым договорам; на странице `/brigadam/` текст пересобирается из `BRIG_TERMS` (генератор), значит изменение в базе
должно **синхронизироваться** с `site-shell.js` — решение: источник истины для страниц — `site-shell.js`; админская форма показывает текущие
значения и предупреждает «после смены — пересобрать страницы и выложить» (до этого сервер применяет старое значение). Не делать два источника.

### 5.14 Что видно на телефоне (админ)
Дашборд «Требует действия» и цифры денег; карточка заказа проекта (Обзор, Лента, Деньги: задать сумму, отметить оплату, «напомнить об оплате»;
Вопросы: ответ клиента и «учтено»); карточка сделки (лента + действия); спор (ответить/решить); анкета бригады (допустить/вернуть); отметить оплату
счёта; очередь листов (ответить на вопрос); заявка по ПДн (посмотреть срок). Остальное — только десктоп (выпуски, таблицы, экспорт, настройки).

### 5.15 Журнал действий (сводно)
Один журнал `br_audit` (переименовать в `audit` при объединении админок) для **всех** частей: админ, модератор, клиент, бригада, система.
Фильтры: кто (роль/человек), объект (заказ, сделка, бригада), вид (деньги, подписи, статусы, ПДн, вход, настройки), период. Записи только
добавляются. На каждом объекте (заказ, сделка, бригада) — вкладка «Журнал» с отфильтрованным видом. Хранение — 5 лет для денег и подписей,
1 год для входов.

## 6. Краевые случаи (решения)

| # | Ситуация | Решение |
|---|---|---|
| 1 | Клиент не выбирает бригаду | Напоминания 3/7/12 дн; на 14-й `expired`, бригадам «клиент не выбрал», предложения `stale`. «Запросить заново» — одной кнопкой |
| 2 | Клиент не подписывает договор | Напоминания 2/5 дн; на 7-й версия просрочена, `contract`; бригада видит «клиент не подписал» и может «Отказаться без последствий» (не считается отказом) |
| 3 | Бригада не подписывает | То же; на 7-й клиенту предлагается выбрать другую из прошлых предложений; бригаде сигнал `sign_timeout` |
| 4 | Бригада пропала после аванса | Клиент: «Бригада не выходит на связь» → спор «срок» → админ звонит/пишет 3 р.дн → нет ответа: приостановка бригады, клиенту рекомендация расторгнуть + шаблон претензии + пакет доказательств (5.5) + подбор новой бригады на остаток. Деньги offsite не возвращаем (не держим), честно говорим это в условиях; в Безопасной сделке аванс бы лежал на сделке — это аргумент для её включения |

## 9. Решения, нужные от Александра
1. База комиссии: работы **и** материалы бригады (предложено) или только работы.
2. Сроки по умолчанию: ответ бригад 3 р.дн, выбор 14 дн, подпись 7 дн, счёт 10 дн, лестница долга 14/30/60 — подтвердить.
3. **Молчание клиента при приёмке этапа = принято** через `stage_silence_days` — предложено 5 р.дн (скрытые работы 3, обжалование 5); или 0 — без автоприёмки.
4. Споры: ответ 5 р.дн, предложение решения + 2 р.дн на согласие — подтвердить.
5. **Защита связи клиент–бригада** 24 мес. — да/нет; **«выкуп» выхода** `exit_fee` (вариант 5 %, мин. 15 000 ₽) — включать или держать выключенным.
6. Лимит конкуренции: пакет получают 6 бригад, клиент видит 5 предложений — подтвердить.
7. Срок хранения договоров 5 лет — подтвердить с юристом.
8. Выезд практика в споре: цена и кто платит.
9. Бригады-НПД: допускаем с ограничениями (предложено) или только ИП/ООО.
10. Подбор бригады по **первому (предварительному)** альбому — разрешить с плашкой (предложено) или только после финального.
